PROJECT 02 / ENGINE DEVELOPMENT

Bomberman.

A Bomberman-style arcade game running on my own C++ engine, built on top of the Minigin framework with SDL3. Solo, Co-op and PvP.

MY ROLE
Engine & game programmer
CONTEXT
Individual project
TECHNOLOGY
C++ / SDL3 / MINIGIN
View source ↗

01

My contribution

I built both the engine and the game. On top of Minigin I added systems for scenes, components, input, audio, collisions, resources, events and save data, and got to put patterns like a state stack, a service locator and observers to real use.

The final stretch was rushed, and funnily enough, some of my favourite ideas were born in those last hours before the deadline.

02

A stack for menus and gameplay

The problem. The game moves between a title screen, menus, gameplay, a game-over screen and a leaderboard. Some screens need to sit on top of others without destroying what’s underneath.

What I considered. A plain state machine (an enum and a switch) would cover a straight line from title to game to game over. But every screen would need to know where to go next, and going back would mean rebuilding a screen from scratch.

What I chose. A stack of game states with three operations: Push puts a screen on top and keeps the one below alive, Pop returns to it exactly as it was, and Change swaps the top screen. Transitions are queued rather than applied the moment they’re requested.

The result. One structure runs every part of the game outside the gameplay itself, and adding a new screen means writing one new state. One of my favourite parts of the project.

03

A leaderboard with a bit of fairy dust

The problem. An old-school arcade game needs a leaderboard: initials, a score, and a top five that survives closing the game.

What I considered. The obvious route is a text or JSON file with the name and the full score. Easy to read, easy to debug, and bigger than it needs to be.

What I chose. Retro programming taught me to be petty about memory, and I wasn’t going to let that go to waste. Every score in my game is a multiple of 100, so I store score ÷ 100 in a 16-bit integer instead of the full score in 32 bits. At the end of a game there’s a single eligibility check and a sort, then the three initials and the score go into a binary file and come back out as a formatted top five.

The result. Each entry (3 initials + score) shrinks from 7 bytes to 5, and the cap still sits at 6.5 million points. Does it matter on modern hardware? Not in the slightest. I did it because I could, and I had fun. As a friend put it: This would make a Nintendo cartridge shed a tear of joy.

04

Looking back

The leaderboard? I’d do it exactly the same way again. Why not? Some other choices were deliberately simple too, like plain rectangle intersection tests for collisions, which was all a grid-based game really needed.

The rushed ending did leave its marks, though. Code cleanup and consistency are the first things I’d improve.
